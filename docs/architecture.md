# 设计说明

![架构](architecture.svg)

## 1. 消息怎么流动

```
设备 ──MQTT/HTTP/TCP──▶ 接入层 ──▶ UplinkProcessor ──▶ EventBus ──┬─▶ telemetry-store  批量写时序表
                                       │ 物模型校验、限流、日志     ├─▶ event-store      事件入库
                                       │                           ├─▶ shadow           合并影子、清除已生效的期望值
                                       │                           ├─▶ rule-engine      评估规则、告警、动作
                                       │                           ├─▶ command / ota    应答与进度、上线补发
                                       │                           └─▶ realtime         WebSocket 推送
设备 ◀──────────────────────────────── DownlinkService ◀── 指令 / 影子 / OTA 服务
```

- **所有设备数据只在 `UplinkProcessor` 里校验一次**，三种接入方式（MQTT / HTTP / TCP）共用它，所以行为一致。
- **总线是唯一的解耦点**：消费者之间互不影响，一个慢（或挂掉的）消费者不会拖住接入。
  - 内存实现：每个订阅者独立的有界队列和线程；同一设备的消息落在同一分区线程里，**保证单设备有序**；队列满了丢弃并计数（`hyperiot_bus_dropped_total`），宁可丢数据也不让接入层 OOM。
  - Kafka 实现：每种消息一个 topic，key 是设备 ID（同设备同分区，保序）；订阅者是消费者组，多节点自动分摊。`hyperiot.bus.type=kafka` 切换。
- 实时推送（WebSocket）每个节点用独立的消费者组——每个节点都要看到全部消息来服务自己的连接。

### 在线状态

- 内置 Broker：Moquette 的连接 / 断开拦截器。重连时旧连接的断开事件可能晚于新连接的建立，处理时会检查该 clientId 是否仍在线，避免误标离线。
- 外接 EMQX：订阅 `$SYS/brokers/+/clients/+/connected|disconnected`，或由 EMQX 调用 `POST /api/mqtt/event`。
- HTTP 设备：首次上报视为上线，5 分钟无上报视为离线。TCP：连接生命周期。
- 平台重启时，所有 `ONLINE` 设备先重置为 `OFFLINE`（重启后没人连着），设备重连后恢复。

## 2. 物模型校验

| 情况 | 处理 |
| --- | --- |
| 类型不对、越界、枚举值不在列表 | 该属性被拒绝，同一条消息里合法的属性照常处理 |
| 属性未在物模型中声明 | 默认拒绝（`hyperiot.model.strict=false` 时透传数字 / 布尔 / 短字符串） |
| 设备带了 `id` | 平台回 `post_reply`：`code=200` 或 `400`（含原因） |
| 被拒绝的原因 | 写入设备日志，控制台可见 |

时间戳：设备给的 `ts` 在“过去 7 天到未来 5 分钟”之内才被采用，否则用接收时间——设备时钟错乱不会污染时序数据。

## 3. 设备影子

- `reported`：每个属性的最新值和时间戳；**乱序保护**——更旧的上报不会覆盖更新的值。
- `desired`：控制台 / API 设置的期望值，只允许 `access=rw` 的属性，写入时立即落库。
  - 设备在线：立即下发 `thing/property/set`；离线：上线时下发。
  - 设备上报了相同的值 → 该项期望值被清除（认为已生效）。
- `reported` 在内存里合并，**每秒批量回写**数据库（写回缓存）；停机时刷新。脏数据持有强引用，不会被缓存淘汰丢掉。
- **限制**：缓存是进程内的。多节点时期望值虽然写库，但其它节点的缓存不会立刻感知；需要共享状态请等 Redis 实现，或把设备按分区固定到节点（Kafka 同设备同分区正好满足）。

## 4. 指令状态机

```
        invoke（设备在线）           设备应答 code=200
 PENDING ───────────────▶ SENT ──────────────────────▶ SUCCESS
    │  ▲                    │   设备应答 code≠200 ─────▶ FAILED
    │  └── 下发失败回退 ─────┘   超过 reply-timeout ────▶ TIMEOUT
    └── 设备离线：排队，上线时补发；超过 TTL ───────────▶ TIMEOUT
```

- **先占位再发送**：`PENDING → SENT` 是一条带条件的 `UPDATE`，成功的一方才真正发送。两个节点同时响应“设备上线”事件也不会把同一条指令发两遍；发送失败则回退到 `PENDING`。
- 应答按 `requestId` 匹配，并校验应答的设备就是被下发的设备（防止设备 A 应答设备 B 的指令）。
- `wait=true` 时 API 阻塞等待应答，超时返回当前状态（指令仍在继续）。
- 参数按物模型里服务的入参校验：类型、范围、必填、不允许多余参数。

## 5. 规则与告警

- 规则只在**所依赖的属性出现在本次上报里**时才评估，不会因为别的属性变化重复评估。
- 评估使用的是“影子里的最新值 ⊕ 本次上报的值”，所以多条件规则（`temperature > 80 AND humidity < 20`）在两个属性分别上报时也能正确判断。
- **告警去重**：同一规则、同一设备同时只有一条活跃告警（`ACTIVE` / `ACKED`）；条件不再满足时自动转 `RECOVERED`。动作（下发指令、Webhook）只在新告警产生时执行一次。
- 比较符：数值支持 `GT/GE/LT/LE/EQ/NE`，布尔 / 字符串 / 枚举只支持 `EQ/NE`；保存规则时按物模型校验。
- **Webhook 的 SSRF 防护**：只允许 http(s)，默认拒绝回环 / 内网 / 链路本地 / 组播地址，不跟随重定向。`hyperiot.webhook.allow-private-addresses=true` 可放开（内网集成场景）。残余风险：DNS 在校验和连接之间被改写（rebinding）——若 Webhook 目标不可信，请在网络层再加一层出口限制。

## 6. OTA

1. 上传固件：按内容的 SHA-256 命名存储（同一文件只存一份），数据库记录版本、大小、校验值；同产品同版本号不可重复。
2. 创建任务：目标设备默认是产品下所有“尚未是该版本”的启用设备；一个设备同时只跟随一个任务（新任务取代旧任务）。
3. 下发：在线设备立即收到 `ota/upgrade`；离线设备保持 `PENDING`，上线时补发。下载地址带 `HMAC(deviceSecret, "ota"+firmwareId+deviceName)` 签名，**不需要登录态，也不暴露其它设备的固件**。
4. 进度：设备上报 `ota/progress`（`step` 0~99 / 100 成功 / -1 失败）或重启后 `ota/inform` 汇报新版本；平台逐设备记录，全部结束后任务转 `COMPLETED`。
5. 卡死：`NOTIFIED` / `DOWNLOADING` 超过 30 分钟无进展 → `FAILED`。

## 7. 安全模型

| 面 | 机制 |
| --- | --- |
| 控制台 / REST | 管理员登录换 JWT（HS256，默认 8 小时）；BCrypt 存密码；登录失败按账号和来源地址限流（5 分钟内 5 / 20 次）；无论用户是否存在都执行一次 BCrypt，响应时间不泄露账号是否存在 |
| WebSocket | 连接后第一条消息带 JWT，10 秒内未认证则断开；Token 不出现在 URL 里；只接受同源浏览器 |
| 设备 MQTT | clientId / username / HMAC 密码三者必须一致；设备被禁用、删除或重置密钥时**立即踢下线** |
| 设备越权 | ACL：只能向自己命名空间的“上行主题”发布（不能伪造平台的下行消息），只能订阅自己命名空间 |
| HTTP / OTA 下载 | 请求体 / 下载地址签名；未知设备与签名错误返回相同的 `401`，不泄露设备是否存在 |
| EMQX 钩子 | 共享令牌 `X-Hook-Token` 常量时间比较；未配置令牌时一律拒绝 |
| 浏览器 | 严格 CSP（`script-src 'self'`）、`X-Frame-Options: DENY`、`nosniff`、无 `innerHTML` 拼接用户数据 |
| 设备密钥 | **明文存库**（服务端要重新计算 HMAC），列表接口不返回；请保护数据库和备份 |

## 8. 数据与保留

- 时序表：`telemetry(device_id, identifier, ts, num_value, str_value)`，`ts` 是毫秒时间戳（整数），聚合就是整数除法分桶，H2 和 PostgreSQL 通用。布尔存为 0 / 1。
- 批量写入：消费者把样本放进 20 万容量的队列，每 500 毫秒或 500 行批量 `INSERT`；队列满则丢弃并告警，不阻塞总线。
- 保留：每天 03:17 删除 `retention-days`（默认 30）天前的样本；设备日志保留 3 天。

## 9. 已知限制（汇总）

- 影子缓存进程内；多节点下告警 / 指令的实时推送只到产生它的节点。
- 内置 Broker 单节点；`listConnectedClients()` 在断开事件里是 O(连接数)，不适合十万级连接。
- 规则没有“持续 N 秒 / 连续 N 次”条件和去抖；没有“设备离线”类告警。
- 指令没有批量下发和设备分组。
- 只有一个管理员角色。
